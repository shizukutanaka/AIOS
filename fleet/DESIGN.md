# AI Fleet — 組織設計（蒸留版）

> 旧 `agent-fleet` の DESIGN.md から、特定マシン固有の運用情報（cron ジョブ ID、
> 実パス、再起動手順）を除き、設計の考え方だけを蒸留したもの。

## 1. 目的（ファーストプリンシプル）

上司 AI（判定役・ボス）と複数の部下 AI（ローカル LLM、クラウド CLI 等）を
並列実行する「AI 組織」を、一個人の PC 上で自律運用する。

**最優先制約: 外部 API のレート制限（HTTP 429）や障害が出ても動き続けること。**
そのためクラウド API への依存を排除し、ローカル中心（Ollama メイン、
代替バックエンド予備）で構成する。ボスはフォールバック経路を常に持ち、
上限に達したルートを避けて部下を振り替える。

## 2. アーキテクチャ（監視チェーン）

```
[失敗検知] → [回路ブレーカー] → [自己検知/自己修復]
   → [ガバナンス: self-edit-gate] → [レジリエンス層]
   → [組織健全性集約] → [学習ループ] → [自己検証ループ]
   → [自己検証結果の人間エスカレーション] → [ボス判定ゲート(git-diff 必須)]
```

| 層 | 実装 | 役割 |
|---|---|---|
| 失敗検知 | `detect_failures.sh` | 失敗シグネチャ（失敗クラス）を定義し、ログ走査で検知。クラスごとに WAIT（待てば回復）/ STOP（止めて直す）を区別 |
| 回路ブレーカー | `detect_failures.sh` + `stop_signal.txt` | 同一失敗が連続 N 回でトリップし、自動実行を一時停止。人間が原因を取り除くまで暴走しない |
| 自己修復 | （外ループ層。本統合では設計のみ） | ゾンビプロセス再起動、内ループ再起動、レート制限時の振替等 |
| ガバナンス | self-edit-gate | 制御コード（ボス/ループ自身）の未承認変更を検出したら退避し、人間レビュー待ちにする。自動化が自分自身を勝手に書き換えない |
| レジリエンス | `router3.sh` | バックエンド上限時は代替へフォールバック |
| 健全性集約 | `fleet_status.sh` 他 | 死活・基盤・資源を集約し HEALTHY/DEGRADED/CRITICAL で出す |
| 学習ループ | `detect_failures.sh` | 失敗を学習ファイルへ構造化追記（シグネチャで重複防止）。同じ失敗を繰り返さない |
| 自己検証 | ガード層（`GUARDS.md`） | 監視者自身を独立に検証する |
| 人間エスカレーション | `fleet_loop.sh` | 連続失敗・同一目標の反復未達は沈黙して捨てず、「人間判断待ち」として記録し表面化させる |
| ボス判定ゲート | `router3.sh` | タスクの期待ファイルに実編集（git diff）が無ければ、部下の「完了」申告を信じず強制差し戻し |

**完了判定の原則**: 完了は自己申告ではなく証拠で判定する。目標には
`done_when:` オラクル（実行可能な完了条件）を付与し、`goal_complete.sh` が
それを実行して初めて完了とする。オラクルが無い目標は「作業ツリーに実変更が
あるか」で代替判定し、それも無ければ失敗として数える。

## 3. 監視する者を誰が監視するか

**組織が自分自身を検証するループ**＋**監視対象の死さえも独立した監視者が検知する**。

- 自己検証は、監視対象のループに従属させない（従属させると監視対象の死と
  共倒れする）。独立したスケジュールから起動する。
- 自己検証は監視ループの heartbeat の鮮度を見る。一定時間更新が無ければ
  「監視者停止」として人間へエスカレーションする。
- これにより単一障害点を排除する: 監視者が黙って死ぬことが最も危険であり、
  「緑は生きていることを証明して初めて緑」である。

## 4. 罠と教訓（過去の痛手から）

1. **テキスト置換の no-op 罠**: `sed`/`awk` は改行コードや全角文字で静かに
   失敗・無変更になることがある。実ファイルへの変更は確実な手段で行い、
   適用後に実ファイルを確認する。「検証ロジックのテストが緑」でも
   「本番ファイルに未適用」のことがある。
2. **fork 枯渇**: 連続した重い検証コマンドはプロセス資源を枯渇させる。
   検証は最小のスクリプトで軽く回す。
3. **self-edit-gate による変更の退避**: 制御コードを直接編集すると、
   ガバナンス層が未承認変更として退避する。制御コードの変更は
   人間承認 → 明示コミットの承認済みフローでのみ適用する。
4. **監視の従属（単一障害点）**: 上記3のとおり、独立化と死活監視で解決。
5. **境界外検査漏れ**: ボスの git-diff 検査は当初フリートのリポジトリ内しか
   見ておらず、別リポジトリでの実作業を「無編集」と誤判定した。
   作業ディレクトリが別 git リポジトリならそちらも検査対象に含める。
6. **未コミット成果の消失感**: 正当な改善が未コミットのまま残ると、
   次セッションで「消えた」ように見える。作業開始時に未コミット変更を
   必ず確認する。

## 5. ボス（上司 AI）の 4 ルール

1. 判断のみ、実作業は部下へ（例外: 部下が誤ったインフラ配線をした場合のみ、
   ボスが単純な配線作業を直接行ってよい）。
2. 全変更ファイルを読んでから判定する（git diff/status ＋ 部下の出力）。
3. 不備は指摘して部下に差し戻し、ボス自身は修正しない。
4. 制御コードの無審査コミットは強行せず、人間の承認を待つ。
